# Releasing Logwell

Releases are cut by tagging. CI builds the files and publishes the GitHub release, using the release notes file as its body. The checks live in `scripts/release-check.mjs`; the tests are in `tests/release/`.

## Version scheme

- While Logwell is in beta, versions are `0.MINOR.PATCH`.
- A milestone or a new feature is a minor bump. Fixes are patch bumps.
- `1.0.0` means feature-complete and listed in the community plugins.
- Releases are marked as pre-releases while the major version is 0.
- Tags are the bare version (`0.2.0`, never `v0.2.0`), as Obsidian requires. `.npmrc` sets `tag-version-prefix=""` so `npm version` tags that way.
- `versions.json` maps each plugin version to the minimum Obsidian version it needs. It is filled in from `manifest.json` `minAppVersion` on every bump.

## Release notes

There is no `CHANGELOG.md`. Release notes live in [`docs/releases/`](../releases/README.md):

- `unreleased.md` collects the entries for the next release. Its header comment states the rules.
- `<version>.md` (for example `0.6.0.md`) is one finished release: a `# <version>` title, a `Released YYYY-MM-DD.` line and the entries under `## Added`, `## Changed`, `## Fixed` and `## Security` (`## Removed` is accepted too). The file is the GitHub release body.
- `README.md` is the index, newest first, generated by the release script. Never edit it by hand.

Rules:

- Every change that a user can notice adds a line to `unreleased.md` in the commit that makes it. Tests, refactors and notes about internals do not.
- When a change comes from a GitHub issue, name the issue and credit the reporter: `- (#12) Fixed ... Thanks to @user for reporting.` A change that does not come from an issue has no number and no thanks.
- A **patch** release may contain only Fixed and Security entries. Anything under Added, Changed or Removed needs a minor bump (a major bump once the version is 1.0.0 or higher).
- Keep the five headings as they are. Empty sections are fine; the release leaves them out of the version file.

## Cutting a release

1. Make sure `main` is clean and green, and `docs/releases/unreleased.md` lists the changes.
2. Run one of:

   ```sh
   npm version patch   # fixes only
   npm version minor   # milestones and features
   ```

3. Push the commit and the tag:

   ```sh
   git push --follow-tags
   # or: git push && git push --tags
   ```

4. CI creates the release. Check the Actions tab, then the Releases page.

`npm version` does this, in order:

1. **preversion**: `node scripts/release-check.mjs pre`, then typecheck, lint and unit tests. The bump type comes from npm (`npm_new_version` against `npm_old_version`). You can also run `node scripts/release-check.mjs pre patch` by hand. It fails when `unreleased.md` has no entries, has an unknown heading or loose entries, carries Added, Changed or Removed entries in a patch, or when `docs/releases/<new version>.md` already exists.
2. npm bumps `package.json` and `package-lock.json`.
3. **version**: `node scripts/release-check.mjs version <new version>` writes `docs/releases/<version>.md` (title, date and the entries that exist, without the empty sections), puts `unreleased.md` back to its empty template, regenerates `docs/releases/README.md`, sets the `manifest.json` version, adds the version to `versions.json`, and stages those five files. npm stages `package.json` and the lock file itself.
4. npm commits and tags.

If the pre check fails, nothing has changed yet. Fix `unreleased.md`, commit, and run `npm version` again. The version step checks everything before it writes anything, so a failure there leaves the files as they were (npm has already bumped `package.json`: run `git checkout package.json package-lock.json`).

Run `npm run e2e` locally before a release. CI does not run it, because it needs a real Obsidian window.

## What CI checks

**CI workflow** (`ci.yml`, on pushes to `main` and pull requests): typecheck, lint, unit tests, and `release-check.mjs lint`, which checks that `unreleased.md` has only the allowed headings and that `docs/releases/README.md` lists exactly the release files.

**Release workflow** (`release.yml`, on a tag like `0.2.0`) runs in two stages. The second starts only if the first passes.

1. **Checks:** the CI workflow itself (typecheck, lint, unit tests and the release notes lint), run on the tagged commit.
2. **Release:**
   1. `release-check.mjs verify <tag>` fails unless the tag is `x.y.z` with no prefix, equals the `manifest.json` and `package.json` versions, is listed in `versions.json`, and has a `docs/releases/<tag>.md` with the right title and at least one bullet. It prints the entries of that file, which become the release notes (`notes.md`).
   2. The production build.
   3. A build provenance attestation for `main.js`, `manifest.json` and `styles.css`.
   4. `gh release create` with those three files and the notes, as a pre-release while the major version is 0.

## Gated release steps for agents

Preparing a release does not authorize pushing, tagging, publishing, commenting on GitHub issues or closing them. An agent prepares the work, reports, and stops. The user pushes the tag and decides which issues to close or comment on. Closing an issue normally happens through the merged pull request that says `Closes #<n>`.

## Before the public submission

Logwell is not in the community plugin list yet. Submission needs:

- a public repository (also what makes BRAT installs possible);
- a `LICENSE` file (done: MIT);
- a `README.md` that says what the plugin does;
- `manifest.json` with a permanent id (`logwell`), a description that does not mention Obsidian or "This plugin" and ends with punctuation, and a version that matches the release tag;
- a GitHub release whose tag equals the manifest version and which carries `main.js`, `manifest.json` and `styles.css`;
- a submission at community.obsidian.md, following the current guidelines there.
